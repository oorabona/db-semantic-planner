# DDL-PROV: DDL Provisioning — push, migrate, verify

## 1. User Story

**As a** developer using db-semantic-planner,
**I want** a complete DDL lifecycle (`push`, `migrate`, `verify`) from the `dbsp` CLI,
**so that** I can provision databases, track schema changes, and detect drift without external tools.

## 2. In-Scope

| Command | Purpose | Mode |
|---------|---------|------|
| `dbsp push` | Sync schema → DB (additive only) | Dev / prototyping |
| `dbsp migrate dev` | Generate migration file from schema↔DB diff | Development |
| `dbsp migrate apply` | Apply pending migrations with tracking | Staging / Production |
| `dbsp migrate status` | Show migration state (applied/pending) | Any |
| `dbsp verify` (enriched) | Full drift detection (FK, indexes, defaults) | CI / audit |

## 3. Out-of-Scope

- DOWN migrations (rollback SQL) — future, manual workaround: write reverse SQL
- Data migrations — DDL only, no DML
- DDL extensions (CHECK, ENUM, partial indexes, comments) — P4 backlog
- MCP server (E06/E06b) — deprioritized to P4
- Multi-dialect — PostgreSQL only
- Squash/rebase migrations — future
- Interactive migration editing — user edits SQL files directly

## 4. Architecture

### 4.1 Shared Comparison Engine

The core of all 3 features is a **schema comparison engine** in `packages/adapter-pgsql/src/ddl/`:

```
                  ┌─────────────────────────────┐
                  │   Schema Definition (ModelIR) │
                  └──────────────┬──────────────┘
                                 │
                  ┌──────────────▼──────────────┐
                  │   Comparison Engine          │
                  │   (schema-diff.ts)           │
                  │                              │
                  │   compare(schema, db) →      │
                  │     SchemaDiff {             │
                  │       changes: Change[]      │
                  │       isDestructive: boolean │
                  │     }                        │
                  └──┬───────────┬──────────┬───┘
                     │           │          │
              ┌──────▼──┐  ┌────▼────┐  ┌──▼───────┐
              │  push    │  │ migrate │  │  verify  │
              │ (exec)   │  │ (file)  │  │ (report) │
              └─────────┘  └─────────┘  └──────────┘
```

**Not a new package** — lives in `packages/adapter-pgsql/src/ddl/` alongside existing DDL code. No new workspace package needed.

### 4.2 Change Types

```typescript
type ChangeKind =
  // Tables
  | 'create_table'
  | 'drop_table'
  // Columns
  | 'add_column'
  | 'drop_column'
  | 'alter_column_type'
  | 'alter_column_nullable'
  | 'alter_column_default'
  // Constraints
  | 'add_primary_key'
  | 'drop_primary_key'
  | 'add_foreign_key'
  | 'drop_foreign_key'
  | 'alter_foreign_key'   // onDelete changed
  // Indexes
  | 'create_index'
  | 'drop_index';

interface SchemaChange {
  readonly kind: ChangeKind;
  readonly table: string;
  readonly column?: string;
  readonly destructive: boolean;  // true for drop_*, alter_column_type
  readonly sql: string;           // The DDL statement
  readonly details?: string;      // Human-readable description
}

interface SchemaDiff {
  readonly changes: readonly SchemaChange[];
  readonly hasDestructive: boolean;
  readonly summary: {
    readonly tables: { added: number; dropped: number };
    readonly columns: { added: number; dropped: number; altered: number };
    readonly indexes: { added: number; dropped: number };
    readonly constraints: { added: number; dropped: number; altered: number };
  };
}
```

### 4.3 Migration Tracking Table

```sql
CREATE TABLE IF NOT EXISTS _dbsp_migrations (
  id          SERIAL PRIMARY KEY,
  filename    TEXT NOT NULL UNIQUE,
  checksum    TEXT NOT NULL,
  applied_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 4.4 Migration File Format

```
migrations/
├── 20260212143000_initial.sql
├── 20260212150000_add_orders_table.sql
└── 20260213090000_add_user_email_index.sql
```

Each file is pure SQL, executable via `psql -f`. Header comment for traceability:

```sql
-- Migration: 20260212143000_initial
-- Generated by: dbsp migrate dev
-- Schema: dbsp.schema.ts
-- Date: 2026-02-12T14:30:00+01:00

CREATE TABLE "users" (
  "id" SERIAL,
  ...
);
```

## 5. Command Specifications

### 5.1 `dbsp push`

**Purpose:** Dev mode — sync schema to DB, additive only.

```bash
dbsp push [OPTIONS]

Options:
  -s, --schema <path>       Schema file (default: auto-detect)
  --db <url>                Database URL (or DATABASE_URL env)
  --schema-name <name>      DB schema namespace (default: public)
  --drop                    Drop and recreate all tables (requires --yes)
  --dry-run                 Print SQL without executing
  --yes                     Skip confirmation for destructive ops
  --casing <type>           snake | camel | none (default: snake)
```

**Behavior:**

| Scenario | Action |
|----------|--------|
| Table missing in DB | CREATE TABLE |
| Column missing in DB | ALTER TABLE ADD COLUMN |
| Index missing in DB | CREATE INDEX |
| FK missing in DB | ALTER TABLE ADD CONSTRAINT |
| Table exists, no changes | Skip (idempotent) |
| Column exists with different type | **Skip** (additive only — use `migrate` for changes) |
| Extra tables/columns in DB | **Ignore** (additive only) |
| `--drop` flag | DROP all + recreate from scratch |

**Transaction:** All DDL wrapped in single `BEGIN`/`COMMIT`. Rollback on any error.

**Safety:**
- `--drop` requires `--yes` or interactive confirmation
- `--dry-run` prints SQL to stdout, exits 0
- Without `--drop`, never destructive

**Exit codes:** 0 = success, 1 = error

### 5.2 `dbsp migrate dev`

**Purpose:** Generate a versioned migration file from schema↔DB diff.

```bash
dbsp migrate dev [OPTIONS]

Options:
  -s, --schema <path>       Schema file (default: auto-detect)
  --db <url>                Database URL (or DATABASE_URL env)
  --schema-name <name>      DB schema namespace (default: public)
  --name <name>             Migration name (default: prompt)
  --allow-destructive       Include DROP TABLE/COLUMN in migration
  --migrations-dir <dir>    Migrations directory (default: ./migrations)
  --casing <type>           snake | camel | none (default: snake)
```

**Behavior:**

1. Introspect database
2. Compare schema definition against DB (comparison engine)
3. If no diff → print "No changes detected", exit 0
4. If diff has destructive changes AND no `--allow-destructive`:
   - Print destructive changes as errors
   - **FAIL** with exit code 1 (do NOT generate a partial migration)
   - Error: "X destructive changes detected. Use --allow-destructive to include them."

> **LLM Review finding (HIGH):** Silent skip of destructive changes is dangerous.
> A partial migration silently omits DROPs → DB accumulates orphan objects.
> Fail-fast forces the developer to make an explicit decision.
5. Write migration file: `migrations/<timestamp>_<name>.sql`
6. Print summary: "Created migrations/20260212143000_add_orders.sql (3 changes)"

**Filename format:** `YYYYMMDDHHMMSS_<name>.sql`
- Name sanitized: lowercase, alphanumeric + underscore
- If `--name` not provided, derive from changes (e.g., `add_orders_table`)

### 5.3 `dbsp migrate apply`

**Purpose:** Apply pending migrations in order, with tracking.

```bash
dbsp migrate apply [OPTIONS]

Options:
  --db <url>                Database URL (or DATABASE_URL env)
  --schema-name <name>      DB schema namespace (default: public)
  --migrations-dir <dir>    Migrations directory (default: ./migrations)
  --dry-run                 Print pending migrations without applying
  --yes                     Skip confirmation
```

**Behavior:**

1. Ensure `_dbsp_migrations` table exists (create if not)
2. Scan `migrations/` directory for `.sql` files
3. Sort by filename (timestamp ordering)
4. For each file:
   a. Check if filename exists in `_dbsp_migrations`
   b. If applied: verify checksum matches (warn if changed)
   c. If pending: execute SQL in transaction, record in tracking table
5. Print summary: "Applied 2 migrations (3 already up to date)"

**Checksum validation:**
- SHA-256 of file content
- If checksum mismatch on applied migration → **ERROR** (file was modified after apply)
- User must resolve manually (reset migration table or revert file)

**Transaction:** Each migration file is its own transaction (not all in one — allows partial progress).

**Exit codes:** 0 = success, 1 = error, 2 = checksum mismatch

### 5.4 `dbsp migrate status`

**Purpose:** Show migration state.

```bash
dbsp migrate status [OPTIONS]

Options:
  --db <url>                Database URL (or DATABASE_URL env)
  --schema-name <name>      DB schema namespace (default: public)
  --migrations-dir <dir>    Migrations directory (default: ./migrations)
  --json                    Machine-readable output
```

**Output (table format):**

```
Migration Status (5 total, 3 applied, 2 pending)

  ✅ 20260212143000_initial.sql              applied 2026-02-12 14:30
  ✅ 20260212150000_add_orders.sql            applied 2026-02-12 15:00
  ✅ 20260213090000_add_email_index.sql       applied 2026-02-13 09:00
  ⏳ 20260214100000_add_reviews.sql           pending
  ⏳ 20260214110000_add_shipping.sql          pending
```

### 5.5 `dbsp verify` (enriched)

**Purpose:** Full drift detection — all schema metadata.

Current verify checks: tables, columns, types, nullable.
**New checks added:**

| Check | Severity | Details |
|-------|----------|---------|
| PK mismatch | error | Wrong PK columns or missing PK |
| FK missing in DB | error | Schema defines FK, DB doesn't have it |
| FK extra in DB | warning | DB has FK not in schema |
| FK onDelete mismatch | warning | CASCADE vs SET NULL etc. |
| Index missing in DB | warning | Schema defines index, DB doesn't have it |
| Index extra in DB | info | DB has extra index (usually fine) |
| DEFAULT mismatch | info | Schema default differs from DB default |
| UNIQUE mismatch | warning | Schema has unique, DB doesn't (or vice versa) |

**Migration tracking check** (new):
- If `_dbsp_migrations` table exists, also report pending migrations count
- Flag: "2 pending migrations. Run `dbsp migrate apply` to apply."

**What it does:**

2. Add query against `pg_constraint` to fetch unique constraints
3. Filter out implicit indexes (PK-backing indexes auto-created by PostgreSQL)
4. Populate `ModelIR.tables[].indexes` with real data instead of `[]`

**Tests:**

**Exit criteria:**

### Block 3: `dbsp push` (`packages/cli`)

**Files:**
- `packages/cli/src/commands/push.ts` — NEW
- `packages/cli/src/ddl-executor.ts` — NEW: transaction-wrapped DDL execution

**What it does:**
1. Load schema, connect to DB
2. Introspect current state
3. Use comparison engine to find missing objects
4. Generate DDL for missing objects only (additive)
5. Use `CREATE INDEX IF NOT EXISTS` for idempotent index creation
6. Execute in transaction (or dry-run)
7. With `--drop`: use existing `generateDDL()` with `includeDropStatements`
   - **Exclude `_dbsp_migrations` table from DROP** (preserve migration history)
8. Print warnings for non-additive changes detected but skipped (type changes, extra columns)

> **LLM Review findings (HIGH):**
> - `push --drop` must NOT drop `_dbsp_migrations` — migration history would be lost
> - `CREATE INDEX IF NOT EXISTS` needed for idempotent push (avoid error on re-push)
> - Skipped non-additive changes should be visible as warnings, not silent

**Tests:**
- `push.test.ts` — unit tests (mock adapter)
- E2E: push to empty DB → introspect → verify matches

**Exit criteria:**
- Empty DB → push creates all objects
- Push twice → second is no-op (indexes use IF NOT EXISTS)
- `--drop` recreates from scratch but preserves `_dbsp_migrations`
- `--dry-run` prints SQL, doesn't execute
- Transaction rollback on error
- Non-additive differences produce visible warnings

**Dependencies:** Block 1

### Block 4: Migration Infrastructure (`packages/cli` + `packages/adapter-pgsql`)

**Files:**
- `packages/adapter-pgsql/src/ddl/migration-tracker.ts` — NEW: `_dbsp_migrations` CRUD
- `packages/cli/src/commands/migrate.ts` — NEW: `dev`, `apply`, `status` subcommands
- `packages/cli/src/migration-file.ts` — NEW: file I/O, naming, checksums

**What it does:**
1. `migrate dev`: introspect → diff → write SQL file (fail on destructive without flag)
2. `migrate apply`: acquire session-level advisory lock → scan dir → check tracking table → execute pending → release lock
3. `migrate status`: scan dir + query tracking table → display
4. Checksum validation for tamper detection
5. **Session-level advisory lock**: `pg_advisory_lock(hashtext('dbsp_migrate'))` on `apply`

> **LLM Review finding (HIGH):** Advisory lock must be session-level, not transaction-level.
> Transaction-level locks would be released between per-file transactions, allowing concurrent applies.
> Session-level lock held for entire `apply` operation, released on disconnect.

```
    ↓

    ↓

```

## 8. Non-Functional Requirements

| NFR | Requirement |
|-----|-------------|
| **Safety** | Never destructive without explicit flag (`--drop`, `--allow-destructive`, `--yes`) |
| **Idempotency** | `push` twice = no-op. `migrate apply` twice = no-op. |
| **Transactions** | Push: single transaction. Migrate: per-file transaction. |
| **Observability** | `--dry-run` on push. Human + JSON output on verify/status. |
| **Security** | No credentials in logs. Connection via URL or env var. |
| **Backward compat** | Existing `verify` output format preserved (new fields added). |
| **Performance** | Introspection is 5 queries. Comparison is in-memory. No perf concern. |

## 9. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Column rename detected as drop+add | Wrong migration | Document limitation. Suggest manual edit. |
| Type change data loss (e.g. text→integer) | Data corruption | `--allow-destructive` required. Warning in SQL comment. |
| Concurrent migrate apply | Double-apply | Session-level `pg_advisory_lock(hashtext('dbsp_migrate'))`. |
| Large schema (100+ tables) | Slow introspection | Already 5 queries, scales fine. |
