## §1 Scope

Issue #154 reports three invalid-SQL bugs against `@dbsp/core` / `@dbsp/adapter-pgsql` 1.0.1. Empirical probing on current `main` (compile-only dumps of the exact issue repros) establishes:

| Issue bug | State on main | Action in this story |
|---|---|---|
| 1 — `ref()` in `.filter()` over back-reference over-qualified | **Already fixed** (`buildColumnRef` dotted-path split, `packages/adapter-pgsql/src/handlers/where/utils.ts`) — probe emits `array_agg(uses.id) FILTER (WHERE uses.id IS NOT NULL)` | Real-DB e2e lock only |
| 2 — same target table via two relation paths | **Broken** — 3 concrete defects (below) | Fix + unit + e2e |
| 3 — `raw()` in `.columns()` | **Already fixed** for the supported 2-arg form (probe emits `SELECT dependencies.target_id, COUNT(*) AS count`); 1-arg form throws opaque internal error `Invalid column: column name must not be empty` | Real-DB e2e lock + clear fail-loud message for 1-arg form |

### Bug 2 — observed defects (probe C, exact emitted SQL)

```sql
SELECT file.path AS use_file, file_1.path AS use_file        -- ① 'def_file' alias lost, duplicate output name
FROM uses
JOIN definitions AS definition ON uses.def_id = definition.id
JOIN definitions AS definition_1 ON uses.def_id = definition_1.id   -- ② spurious duplicate JOIN of intermediate table
JOIN files AS file ON definition_1.file_id = file.id
JOIN files AS file_1 ON uses.file_id = file_1.id              -- ③ 4 JOINs instead of 3
```

Root causes (exploration, verified file:line on HEAD):

- **D1 — `findRelationMapKey` (`packages/adapter-pgsql/src/adapter-compiler-select.ts:518`)**: both `includeStrategy` decisions carry the schema-level `relationName='file'`; exact-match wins before suffix-match, so the `'definition.file'` entry of the relation-columns map is never matched — both JOINs receive the `'file'` entry's `columnAliases` (`use_file`).
- **D2 — `joinAliasMap` keyed by `targetTable` (`packages/adapter-pgsql/src/compiler.ts:851`)**: any N≥2 joins on the same physical table overwrite each other's entry; downstream multi-hop ON-clauses resolve `joinAliasMap.get(decision.sourceTable)` by BARE table name (`compiler.ts:798`), so the last-registered alias wins for every subsequent hop.
- **D3 — multi-hop include re-anchors the intermediate join**: `include('definition')` + `include('definition.file')` emit TWO joins for `definitions` (`definition`, `definition_1`) instead of reusing the existing one. Join identity must be the include PATH, not the emission order.
- **D4 — `usedJoinAliases` never reset per compile** (reality audit): it is a class field (`compiler.ts:480`) never reassigned in `compile()` — only `joinAliasMap` is reset (`compiler.ts:886`). The `_N` counter is globally monotonic across successive compiles on a shared adapter instance: the SAME query can compile to DIFFERENT SQL depending on compile history, violating the determinism NFR (same inputs → same SQL).

### Fix approach (Bug 2)

**Identity invariant (canonical, document in ONE place + lock with a regression test):** join and relation-column identity is the **relation-dotted include path** (`definition.file`, `file`, `manager.manager`) — never the bare target table, never the schema-level relation name alone. ⚠️ The planner's `intentPath` is POSITIONAL (`include[0].include[1]`) and does NOT match the relation-dotted keys of `buildRelationColumnsMap` — it is NOT a substitute. The relation-dotted path must be derived from the relation chain (`sourceTable` + `relationName` ancestry) and threaded onto the `includeStrategy` decision via `toJoinIncludeDecision` (`packages/adapter-pgsql/src/plan-decision-extractor.ts:~1689`). Then:

1. Key the relation-columns map AND its lookup (`findRelationMapKey` / `injectAndValidateRelationColumns`) by relation-dotted path — exact path equality only; DROP the suffix heuristic.
2. Re-key the existing maps (`joinAliasMap`, `usedJoinAliases`) by relation-dotted path; no new registry abstraction. Make BOTH per-compile: `joinAliasMap` is already reset in `compile()` (`compiler.ts:886`); `usedJoinAliases` is NOT (class field, `compiler.ts:480`) — add its reset to the same block (fixes D4). Lock determinism with a test compiling the same query twice on one adapter instance and asserting byte-identical SQL.
3. Deduplicate joins by relation-dotted path: same path → reuse the existing join/alias (fixes ②/③); different paths to the same table → distinct aliases (existing `_N` suffix scheme). Every generated `_N` alias passes `validateIdentifier`, and collision checks consider base aliases AND generated aliases together (a relation literally named `file_1` must not collide with a generated `file_1`).
4. **Duplicate-path conflict semantics (pinned):** the same relation-dotted path included twice with IDENTICAL options dedupes silently to one join; with the SAME join type but different column selections, the projections MERGE (union — nothing silently dropped); with CONFLICTING join types it throws an `InvalidOperationError` naming the path — silent first/last-wins would change row cardinality. Locked by test.
6. **`via`-disambiguated includes are distinct paths:** the path identity is the disambiguated relation chain actually traversed (e.g. `author`, `reviewer`), NEVER the bare target relation/table name — `.include(t, { via: 'author' })` and `.include(t, { via: 'reviewer' })` must produce two joins, two column bindings, two filter scopes. Locked by test asserting SQL AND params.
7. **Hydration is part of the contract:** the core result hydrator (`packages/core/src/dx/result-hydrator.ts`) must consume full relation-dotted fallback keys (multi-segment paths nest, e.g. `definition.file.path` → `definition.file.path` in the hydrated shape) without clobbering sibling relations. Result-SHAPE assertions via `.execute()` against real rows are required wherever fallback keys are asserted — SQL-only assertions are insufficient.
5. **Implicit intermediate joins share the path identity:** `include('definition.file')` alone synthesizes the `definition` join under path `definition`; a later (or earlier) explicit `include('definition')` reuses that same join/alias regardless of include order. ON clauses and hydration keys are path-based, never emission-order-based.

**Aliasing compatibility constraint:** the first occurrence of a relation keeps today's alias (the relation name); only colliding subsequent paths get suffixed (existing `_N` scheme preserved). This keeps current snapshot tests and auto-generated hydration keys (`"rel.col"`) stable for all single-path queries. Run full adapter + core suites to verify zero alias churn outside the multi-path case.

**Hydration-key contract for multi-path includes (pinned here, locked by test):** an explicit `relationColumn(..., as)` alias always wins (unchanged). The auto-generated fallback key stays `"<relationName>.<col>"` when that relation name occurs through exactly one include path in the query (today's behavior, zero churn — covers all nested single-path includes); when the SAME relation name occurs through 2+ paths, the fallback key for each is its full relation-dotted path (`"definition.file.path"` vs `"file.path"`) — deterministic and independent of join emission order (never the mutated `_N` join alias, which leaks emission order).

### Bug 3 DX — fail-loud message

`raw(sqlFragment)` without alias currently throws `Invalid column: column name must not be empty` (internal validator leak). Change to an explicit message at `raw()` entry (`packages/core/src/dx/filters.ts:~809`): alias argument is required and must be a non-empty identifier — e.g. `raw() requires an alias as second argument, e.g. raw('COUNT(*)', 'count')`.

### Out of scope (tracked, not fixed here)

- **Manual `.join()` + `include()` on the same table bypasses join dedup entirely** (`compileJoinDecision` path never consults `usedJoinAliases`). ⚠️ Reclassified by adversarial review as **latent-invalid SQL** (a manual-join alias can collide with an include's `_N` alias and emit a duplicate alias TODAY), not merely "unhandled" → file follow-up GitHub issue at finalize with that framing.
- **`orderBy('rel.col')` dotted plain-string**: probe shows the identifier validator rejects it fail-loud BEFORE SQL emission (no invalid SQL emitted; supported forms are `orderBy(relationColumn(...))` / expression refs). Not a correctness bug. The static-analysis claim that `compileOrderByDecision` would emit `definitions.uses.id` is unreachable through the public API.
- General redesign of the aliasing scheme (NFR "deterministic aliasing" preserved as-is).

## §2 Reality constraints & scope pivots

- The issue was filed against published 1.0.1 (2026-06-08, before the 1.1.x releases). - The issue's literal bug-2 error (`table name "file" specified more than once`) did not reproduce verbatim on HEAD (the `_N` dedup partially fires now); what reproduces is wrong-but-executable SQL: lost `def_file` alias + spurious duplicate intermediate join. The e2e must therefore assert exact SQL + exact result-row shape, not just "no PG error" (a no-error assertion would pass on semantically wrong SQL — PR #99 lesson).
- All three scenarios are real-DB-only failures per the issue; per project memory ("real-DB tests catch what static review locks"), e2e tests in `tests/e2e/` (testcontainers harness, `pnpm test:e2e`) are the acceptance vehicle, written BEFORE the bug-2 fix (red), turned green by it.

## §3 BDD scenarios

### S1 — FILTER over back-reference (lock, expected green pre-fix)
- **Given** schema `definitions(id)` / `uses(id, def_id FK→definitions.id)` with back-reference relation `uses`; seed: D1 with uses U1,U2; D2 with none
- **When** `from('definitions').include('uses',{join:'left'}).columns([fn('array_agg', ref('uses.id')).filter(isNotNull('uses.id')).as('use_ids')]).groupBy(['id'])` executes against real PG
- **Then** compiled SQL contains exactly `array_agg(uses.id) FILTER (WHERE uses.id IS NOT NULL)` (no `definitions.uses.id`), and rows are D1→`[U1,U2]`, D2→`[]`/`NULL` (discriminating: a broken FILTER or JOIN changes D2's row)

### S2 — two relation paths to the same table (red pre-fix, green post-fix)
- **Given** schema `files(id, path)` / `definitions(id, file_id FK→files)` / `uses(id, def_id FK→definitions, file_id FK→files)`; relations: `uses.definition`, `uses.file`, `definitions.file`; seed: F1 `/def.ts`, F2 `/use.ts`, D1→F1, U1→(D1, F2) — paths differ so any alias swap/loss is observable
- **When** `from('uses').include('definition',{join:'inner'}).include('definition.file',{join:'inner'}).include('file',{join:'inner'}).columns([relationColumn('definition.file','path','def_file'), relationColumn('file','path','use_file')])` executes
- **Then** SQL has exactly 3 JOINs: `definitions` once, `files` twice under two distinct aliases; SELECT list carries `AS def_file` and `AS use_file`; the files-via-definition ON anchors on the single `definition` join; result row is `{def_file:'/def.ts', use_file:'/use.ts'}`

### S3 — raw() in columns (lock, expected green pre-fix)
- **Given** schema `dependencies(id, target_id)`; seed: target T1×2 rows, T2×1 row
- **When** `from('dependencies').columns(['target_id', raw('COUNT(*)','count')]).groupBy(['target_id'])` executes
- **Then** rows are `{target_id:T1, count:2}`, `{target_id:T2, count:1}` (counts discriminate)

### S4 — raw() alias fail-loud (unit, core)
- **When** `raw('COUNT(*)')` is called without alias (TS-bypassed), or with `''` / whitespace-only / invalid-identifier alias
- **Then** missing/blank alias throws an error whose message names `raw()` and the required alias argument (not the internal "column name must not be empty"); invalid-identifier alias still goes through existing `validateIdentifier` rejection (the new message must not bypass it)

### S5 — alias-scheme stability (regression guard)
- **When** the full existing adapter-pgsql + core test suites run post-fix
- **Then** zero failures: single-path include aliases and hydration keys are byte-identical to before

### S6 — same relation at two depths, self-referential (unit, compile-only)
- **Given** schema `employees(id, manager_id FK→employees.id)` with relation `manager`
- **When** `from('employees').include('manager',{join:'left'}).include('manager.manager',{join:'left'})` compiles, selecting one column per path
- **Then** SQL has exactly 2 JOINs on `employees` with distinct aliases; the 2nd hop's ON anchors on the 1st hop's alias (not the root, not itself); each path's column carries its own alias

## §5 Test requirements

- e2e: real-DB row assertions + exact-SQL assertions on `dump().sql` (PARAMS included). Never assert mere table-name presence (PR #99 false-positive lesson). Seed discriminating data (memory: rows a buggy compilation would wrongly include/exclude).
- Unit (adapter): compile-only dumps locking the 3 defects D1/D2/D3 separately + S6 (same relation at 2 depths, self-referential) + 3-paths-to-same-table case (D2 generalization) + identity-invariant lock test (join/column identity = relation-dotted include path; a `targetTable`-keyed regression must fail it).
- Multi-path WITHOUT explicit aliases: `relationColumn('definition.file','path')` + `relationColumn('file','path')` (no `as`) — asserts the pinned fallback-key contract (full dotted path on collision, never the suffixed join alias; no duplicate keys). A wrong fix could keep S2 green via explicit aliases while leaking suffixed/duplicate fallback keys.
- Include-order stability: S2's include chain in reversed sibling order produces path-equivalent SQL (same ON anchors, same hydration keys; only deterministic alias assignment may differ) — locks path-based over emission-order-based identity.
- Implicit-intermediate variant: `include('definition.file')` WITHOUT explicit `include('definition')`, then the variant adding `include('definition')` after — both reuse one `definition` join (§1 rule 5).
- Duplicate-path conflict: same path twice with identical options → 1 join; with different join types → throws (§1 rule 4).
- Generated-alias validation: every `_N`-suffixed alias passes `validateIdentifier`; base-vs-generated collision case (relation named `file_1`) asserted compile-only.
- `withSchema('s')` + pagination (exact-SQL assertions, not smoke): schema-qualified range vars on every join, wrapper/subquery alias correctness, multi-hop ON anchors unchanged under both.
- Determinism (D4): same query compiled twice on one adapter instance → byte-identical SQL.
- Churn-risk surface for S5 (existing tests asserting auto-generated keys/aliases, verified by reality audit): `pgsql-adapter.test.ts:994`, `compiler-inner-join.test.ts`, `compiler-left-join.test.ts`, `join.coverage.test.ts`, and `double-alias.test.ts` (already locks single-path no-suffix + two-path `file_1` — read it BEFORE coding B2).
- Full suites: `pnpm test` (all packages) + `pnpm test:e2e` green.
