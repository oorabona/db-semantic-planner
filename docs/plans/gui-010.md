# Specification: GUI-010 — .assert.dbsp Runner with Inline Pass/Fail

## 1. Problem Statement

Users who write `.assert.dbsp` files can only validate them via the CLI (`dbsp --input file.dbsp --assert file.assert.dbsp`). The GUI explorer needs native assertion running so users can visually validate NQL queries against expected SQL, parameters, and database results directly in the desktop app.

## 2. User Stories

**US-01**: As a developer using the GUI explorer, I want to open an `.assert.dbsp` file and run its assertions against my NQL queries so that I can validate query correctness visually.

**US-02**: As a developer without a database connection, I want to run SQL/params-only assertions so that I can validate compilation output without a live DB.

## 3. Business Rules

### 3.1 Invariants

- INV-01: Assertion parsing uses the same logic as CLI (shared code in `@dbsp/core/assert/`)
- INV-02: SQL-only assertions (`sql.*`, `params.*`, `intent.*`) never require DB connection
- INV-03: DB assertions (`db.*`) are skipped (not failed) when no connection is active
- INV-04: Assertion results are per-block, per-assertion granular

### 3.2 Preconditions

- PRE-01: An `.assert.dbsp` file is open in the editor
- PRE-02: The corresponding `.dbsp` query file exists (same base name, e.g., `users.dbsp` ↔ `users.assert.dbsp`)
- PRE-03: For DB assertions: an active database connection with a loaded schema

### 3.3 Effects

- EFF-01: Each assertion block shows pass/fail/skipped status in the results panel
- EFF-02: Failed assertions show expected vs actual diff
- EFF-03: Summary bar shows total/passed/failed/skipped counts

### 3.4 Error Handling

- ERR-01: Parse error in assertion file → show line-specific error, no execution
- ERR-02: Associated `.dbsp` file not found → show error with expected filename
- ERR-03: NQL compilation failure in query file → assertion block shows "query failed" with error
- ERR-04: DB query timeout → individual assertion marked failed with timeout message
- ERR-05: Connection lost mid-run → remaining DB assertions skipped, SQL assertions continue

## 4. Technical Design

### 4.1 Architecture Decision: Shared Assertion Code

**Decision**: Extract assertion-parser + assertion-functions from `packages/cli/src/repl/` to `packages/core/src/assert/`.

**Rationale**:
- assertion-parser: pure string parser, zero external deps
- assertion-functions: only depends on `normalizeSQL` (already in core)
- Avoids CLI→sidecar dependency (CLI has heavy deps: Commander, Ink, etc.)
- Both CLI and sidecar import from core (existing dependency)

**What moves to core**:
- `assertion-parser.ts` → `packages/core/src/assert/assertion-parser.ts`
- `assertion-functions.ts` → `packages/core/src/assert/assertion-functions.ts`
- Types: `AssertionType`, `Assertion`, `AssertionBlock`, `ParseResult`, `ParseError`, `TableAssertionData`, `AssertionOutcome`, `QueryAssertionResult`, `AssertionSummary`
- Shared types: `AssertionQueryResult` (new — sidecar-friendly version of `BatchResult`)
- Barrel: `packages/core/src/assert/index.ts`

**What stays in CLI**:
- `assertion-runner.ts` — thin wrapper that converts `BatchResult[]` → `AssertionQueryResult[]` then calls core
- CLI-specific formatting and output

**New in sidecar**:
- `assertion-handler.ts` — IPC handler that parses .dbsp, compiles NQL, optionally executes, builds results, runs assertion functions

### 4.2 Data Flow

```
Frontend                    Sidecar                         Core
────────────────────────────────────────────────────────────────────
Open .assert.dbsp
  → editor tab (language: 'assert')

Click "Run Assertions"
  → IPC: runAssertions({
      assertContent,             parseAssertionFile()  ←──── core/assert/
      queryContent,                                          parser
      connectionId?              compile NQL queries
    })                           execute (if connected)
                                 build AssertionQueryResult[]
                                 evaluate()  ────────────────→ core/assert/
                                                              functions
  ← results: {                   ← AssertionSummary
      summary,
      results[]
    }

Display in AssertionResults panel
```

### 4.3 New Types (in core)

```typescript
/** Sidecar-friendly query result for assertion evaluation */
export interface AssertionQueryResult {
  query: string;
  success: boolean;
  dbSuccess?: boolean;
  sql?: string;
  params?: readonly unknown[];
  error?: string;
  rowCount?: number;
  columns?: string[];
  rows?: unknown[];
  intent?: {
    type: string;
    table: string;
    with: string[];
    hasWhere: boolean;
    hasGroupBy: boolean;
    hasOrderBy: boolean;
    ctes: string[];
  };
}
```

### 4.4 IPC Method

```typescript
// New router method in sidecar
RunAssertionsParams = v.object({
  assertContent: v.string(),   // .assert.dbsp file content
  queryContent: v.string(),    // .dbsp file content
  connectionId: v.optional(v.string()),
});

// Response
RunAssertionsResult = {
  summary: { total, passed, failed, skipped },
  results: QueryAssertionResult[],
  parseErrors?: ParseError[],
};
```

## 5. Acceptance Criteria (BDD)

### Scenario Group: Assertion Execution

```gherkin
@priority:high @type:nominal
Scenario: SC-01 Run assertions with all passing
  Given a connected DB and schema loaded
  And a .dbsp file with 3 NQL queries
  And a .assert.dbsp file with assertions for all 3 queries
  When I run assertions
  Then the summary shows 3/3 passed, 0 failed, 0 skipped

@priority:high @type:nominal
Scenario: SC-02 Run SQL-only assertions without DB
  Given no active database connection
  And a .dbsp file with NQL queries
  And a .assert.dbsp file with sql.equals and params.equals assertions
  When I run assertions
  Then SQL/params assertions evaluate normally
  And db.* assertions show as "skipped" (not failed)

@priority:high @type:error
Scenario: SC-03 Failed assertion shows diff
  Given an assertion expects sql.equals: SELECT * FROM "users"
  And the actual SQL is SELECT "id", "name" FROM "users"
  When I run assertions
  Then the assertion shows FAILED
  And the expected vs actual values are displayed

@priority:high @type:edge
Scenario: SC-04 Parse error in assertion file
  Given an .assert.dbsp file with invalid syntax on line 5
  When I run assertions
  Then no assertions execute
  And a parse error is shown with line number 5

@priority:medium @type:edge
Scenario: SC-05 Missing associated query file
  Given an .assert.dbsp file open without corresponding .dbsp file
  When I run assertions
  Then an error shows "No query file found: expected [filename].dbsp"

@priority:medium @type:nominal
Scenario: SC-06 NQL compilation failure
  Given a .dbsp file with an invalid NQL query (query 2 of 3)
  When I run assertions
  Then query 2 assertions show "query compilation failed"
  And query 1 and 3 assertions run normally

@priority:medium @type:edge
Scenario: SC-07 DB timeout on query
  Given a DB connection and a slow query
  And a timeout of 5000ms
  When the query exceeds the timeout
  Then the assertion block shows "timeout" as failure reason

@priority:medium @type:nominal
Scenario: SC-08 Empty assertion file
  Given an empty .assert.dbsp file
  When I run assertions
  Then the summary shows 0 total, with message "No assertions found"
```
